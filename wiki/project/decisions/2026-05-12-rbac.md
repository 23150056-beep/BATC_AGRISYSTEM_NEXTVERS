# Role-Based Access Control — Three Roles

## Decision
Implement **three user roles** with strictly scoped permissions:
1. **ADMIN** — full system access (users, programs, inventory, reports)
2. **STAFF** — operational access (register farmers, review apps, distribute goods)
3. **CLIENT (Farmer)** — personal access (apply to programs, view claims, submit feedback)

Role is stored in `User.role` (CharField with choices); enforced via `@permission_classes` decorators on DRF viewsets.

## Context
BATC serves a single municipality with three distinct user types:
- **Admins** (1–2) — set up programs, manage inventory, generate reports
- **Staff** (3–5) — community-facing, register farmers, process applications
- **Farmers** (100–1000) — apply for interventions, receive goods

Each role must have different **data visibility** (what records they can read) and **actions** (what operations they can perform). A single `User` model with a `role` field and permission checks on each endpoint is simpler than Django Groups and avoids permission explosion.

## Options Considered

| Approach | Simplicity | Flexibility | Query Cost | Chosen |
|---|---|---|---|---|
| A (chosen) | Simple | Fixed (3 roles) | O(1) per endpoint | ✅ |
| B | Complex | Very flexible | O(n) (Groups query) | Rejected — overkill |
| C | Very simple | Rigid | O(1) | Rejected — hardcoded role checks in views |

## Rationale

### Single `role` CharField
- **Simpler than Groups+Permissions** — no junction table, no permission name registry
- **Easier to audit** — "staff01 is STAFF" is one column, not a many-to-many lookup
- **Fast filtering** — `User.objects.filter(role=User.STAFF)` is an index-friendly WHERE clause
- **Scope is bounded** — BATC will never need 100+ permission types; three roles cover the domain

### Permission Checks as `@permission_classes` Decorators
```python
class UserViewSet(ViewSet):
    @permission_classes([IsAdmin])
    def create(self, request): ...  # Only ADMIN can create users
    
    @permission_classes([IsStaffOrAdmin])
    def list(self, request): ...    # STAFF and ADMIN can list
    
    @permission_classes([IsClient])
    def me(self, request): ...      # CLIENT can see own profile
```
- **Declarative** — permission intent is visible at method level
- **Reusable** — `IsAdmin`, `IsStaffOrAdmin`, `IsClient` defined once in `core/permissions.py`
- **Composable** — chain multiple permission classes if needed

### Data Scoping via QuerySet Filtering
```python
def get_queryset(self):
    if self.request.user.role == User.CLIENT:
        return Farmer.objects.filter(user=self.request.user)  # Own profile only
    elif self.request.user.role == User.STAFF:
        return Farmer.objects.all()  # All farmers (within their barangay if multi-office)
    elif self.request.user.role == User.ADMIN:
        return Farmer.objects.all()  # All farmers
```
- **Filter at source** — database returns only allowed rows
- **Prevents accidental leaks** — archived records, inactive users, etc. are scope-gated

## Role Definitions

| Action | ADMIN | STAFF | CLIENT |
|---|---|---|---|
| **Users** | CRUD, archive, reset password | List only | Manage own profile only |
| **Farmers** | CRUD, archive | Create (register), read, update, archive | Read own profile |
| **Programs** | CRUD, activate/suspend/complete | Read only | List + apply |
| **Inventory** | Receive, adjust, view all batches | Adjust only | N/A |
| **Applications** | View all + approve/reject/cancel | Review + approve/reject/cancel | Submit + view own |
| **Distribution** | Create, view all, update status | Allocate + deliver | View own claims |
| **Reports** | Download CSV (all data) | Download CSV (limited scope) | N/A |
| **Announcements** | CRUD | Read only | Read only (targeted) |
| **Feedback** | View all | Read own submissions | Submit + read own |

## Consequences

### Enabled
✅ Clear separation of concerns — each role has minimal required permissions  
✅ Easy to explain to stakeholders — "Staff can't create programs" is simple  
✅ Audit-friendly — `user.role` in every ActionLog row  
✅ Scalable to small team growth (ADMIN, STAFF, CLIENT remain sufficient)  

### Constrained
⚠️ No per-farmer-group visibility — all STAFF see all farmers (not filtered by barangay)  
⚠️ No permission granularity — can't give one ADMIN "view-only" on reports without code change  
⚠️ Role changes are rare — designed for 3 permanent roles, not user-managed role switching  

## Future Evolution
If constraints become blockers:
1. **Per-barangay scoping:** Add `staff_barangay` field to User; filter all farmer queries by it
2. **Delegation roles:** Add `SUPERVISOR` role intermediate between STAFF and ADMIN
3. **Permission audit:** Log all authorization decisions (`authenticated_user_id, action, resource_id, granted/denied, timestamp`)

## Testing

1. **ADMIN can CRUD users:** `POST /users/ → 201 Created`
2. **STAFF cannot create user:** `POST /users/ → 403 Forbidden`
3. **STAFF can see users:** `GET /users/ → 200 OK`
4. **CLIENT cannot see users:** `GET /users/ → 403 Forbidden`
5. **CLIENT can see own profile:** `GET /farmers/me/ → 200 OK`
6. **CLIENT cannot see other farmer:** `GET /farmers/{other_id}/ → 403 Forbidden`
